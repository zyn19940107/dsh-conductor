# 团队里最贵的那个人，其实不写代码：我把「领导-执行者」搬进了 AI Agent

## 先讲一个真实的失败

我让 AI 去做一个 15 分钟的任务：玩一局 2048，尽力拼出最大的方块。

AI 很聪明。它读了几行游戏代码，发现这游戏的随机数是**固定种子**的——也就是说，只要走法一样，后面冒出来的方块就完全一样。于是它做了一个决定：**不一个个试，直接写个程序算最优解。**

这个想法完全正确。它甚至算出了要搜多少、大概要多久。

然后它把这个活交给了一个"子 Agent"去做。

结果：**那个子 Agent 跑了 568 秒，占掉整局 76% 的时间，最后什么都没交出来。**

主 Agent 是在超时之后才发现预算被吃光的。它的原话是：

> The worker timed out (540s budget = 9 min!). That ate a lot of my 15-minute budget.

更扎心的是：那个子 Agent **没有偷懒**。它跑了 22 步、30 次工具调用，真的在写代码、调 bug、跑程序。它只是**把时间花在了一个太贵的方向上，而且没有任何人叫它停。**

这次失败之后我明白了一件事：

> **问题不是 AI 不够聪明，而是它干活的方式不像"真实的工作"。**

## 现在的 AI 是怎么干活的

绝大多数 AI Agent（包括我用的 DeepSeek Harness，一个开源的 agent 运行框架）都是这个循环：

```
想一步 → 调一个工具 → 看结果 → 再想一步 → 再调一个工具 → …
```

这里的「调工具」可以理解为：读一个文件、跑一条命令、搜一次网页。

这个循环适合**短任务**。但一旦任务长一点，就会暴露几个很现实的问题：

**① 串行。** 明明三件互不相干的活，也要排队一件件做。

**② 上下文越滚越大。** 每走一步，都要把之前所有内容重新"看"一遍。走几十步之后，AI 脑子里塞满了中间结果，还经常忘记自己三步前读过什么，于是同一个文件反复读。

**③ 没人管时间。** AI 看不见钟表。它只能"估"自己还要多久，而且估得经常不准。一个活干多久，全凭它觉得"差不多了"。

**④ 结果会被悄悄截断。** 结果太长时，系统会只留头尾。但 AI 不知道中间被切了，它以为那就是全部。

**⑤ 最重要的一点：真实工作根本不是这么组织的。**

## 真实工作里，最贵的那个人不写代码

想想你在公司接一个需求会怎么做：

1. 你不会立刻打开 IDE 开始写代码。你会先**想清楚这活怎么拆**；
2. 然后**决定每一块交给谁**：自己干？给一个纯执行的同学？还是给一个也会自己拆活的同事？
3. 交代的时候一定会说三件事：**要做什么、多久要、回什么结果给我**；
4. 接到活的人**可能继续当领导**（自己再拆一层），也可以只是纯干活。

**领导的价值不在于他动手，而在于：他决定怎么分、分给谁、什么时候要、以及拿回来的东西够不够做决定。**

我把这套结构直接搬进了 DeepSeek Harness，做成一个插件，叫 **dsh-conductor**（中文名「**公司工作流**」）。

## 设计：一个领导，四种执行者

插件的核心是：**每一轮，主模型先当领导，不碰工具，只负责画一张"工作安排图"，然后交给执行者；执行者的结果收回来，领导再决定下一步。**

执行者分四种：

| 执行者 | 相当于公司里的谁 | 干什么 |
|---|---|---|
| `tools` | 纯执行的人 | 你告诉他具体做哪几件小事（读这几个文件、跑这几条命令），他照做，不思考不拆解 |
| `worker` | 干活型的人 | 给了他背景和目标，他自己想办法干完，但不会再往下分 |
| `spawner` | 刚招进来的新人 | 从零开始，自己拆自己的活，可能再当一次领导 |
| `forker` | 看过项目资料的新人 | 和新人一样能拆活，但他**已经读过你之前看的资料**，不用重复看 |

### 为什么要有两个"新人"

这是最多人问的问题。

**`spawner` 是白纸**：他看不到你之前的对话、读过的文件、查到的线索，你得把背景都写进任务里。好处是他脑子里干净、不受你之前的思路影响，适合真正独立的活。

**`forker` 是带着资料入职的**：他能看到你到目前为止的所有上下文——你读过哪些文件、发现过什么线索。好处是他上手快，不用重复劳动。

区别就是：**要不要继承当前对话**。

### 一张图长什么样

模型每轮交的东西大概是这样（截断版）：

```json
{
  "criteria": ["说清每个 spec 实际测的是哪个入口", "给出 src 下的证据"],
  "nodes": [
    { "id": "read-specs", "kind": "tools", "budgetMs": 60000,
      "calls": [{ "name": "read", "arguments": { "file_path": "test/a.spec.ts" } }] },
    { "id": "read-src", "kind": "tools", "budgetMs": 60000,
      "calls": [{ "name": "read", "arguments": { "file_path": "src/tool.ts" } }] },
    { "id": "judge-it", "kind": "worker", "budgetMs": 90000,
      "task": "根据前两个节点的结果，判断每个 spec 测的是哪个入口" }
  ]
}
```

几个关键点：

- **判据**（criteria）：这一轮什么算成功，模型自己写；
- **节点**：每个节点是什么执行者、要花多久、干什么；
- **`budgetMs`**：这个节点预计花多久——后面会讲，这是整个 v2.3 的核心；
- **只有一层**：所有节点同时开始，不搞复杂的依赖图。需要串联的活，留到下一轮。

## 为什么这些必须是「机制」，不能只是「提示」

这是我在开发中感受最深的一点。

**写在提示词里的要求，AI 会当成背景音。** 我试过把同样的要求放在系统提示词的不同位置——改位置没用。真正有用的只有两种做法：

1. 把它做成**模型说话前最后读到的那条消息**；
2. 或者做成**关键节点上的硬拦截**。

所以我做了几件事：

**① 每一轮开始前，把"四步循环"作为最后一条消息塞给模型。** 它说话前最后读到的才是它真会照做的。

**② 图跑完之后，模型自己调工具一律拒绝。** 那一刻它是"领导在看结果"，只能做两件事：写结论，或者交下一张图。不许再自己动手——那是图里的活。

**③ 派活只能走图。** 系统自带的"直接开子 Agent"的接口会被拦掉，提示它改成图里的节点。否则它会绕过整个结构，那等于没有结构。

**④ 计划结果永远不截断。** 图跑完后所有节点的结果是领导做判断的唯一依据。如果这份结果被截断，中间某个节点就等于**静默消失**了——领导不知道自己少看了东西。

**⑤ 后台子 Agent 的管理工具直接不给。** 计划节点是同步的，没有"后台"这回事。给了这些工具，模型只会拿着它空转——我实测有样本在"等 120 秒"里循环了 47 步。

## v2.3 的核心：每个节点都要说"我大概花多久"

这就是开头那个 568 秒事故的直接产物。

先说清楚问题的本质：**AI 看不见钟表，它只能推测。** 所以"慢"本身不是最糟的——最糟的是「**慢，而且最后什么都没留下**」。

直接杀掉是最差的选择：节点做了一半的东西全部作废，领导也不知道它做到哪。

我的做法是：**图里每个节点都声明一个"预计花多久"。到点了，先停下，再让它自己交代。**

- 对 `tools` 节点（纯执行）：停掉还没跑完的命令，**保留已经跑完的**，在结果末尾标一句"预算用尽，未完成的已停止"；
- 对另外三种（会思考的）：**先停下它当前的回合**（正在等的那条命令也会被中止），然后给它一条消息——**花了多少、还剩多少、两种选择的后果**——让它自己决定：是赶紧收尾，还是报告现状结束。

那条消息不是一句"你看看状态"，而是给出它做判断需要的数字：

> 你的节点预算 20 秒已用完，正在进行的工作刚被停下。你现在最多还有 45 秒。
> - 如果剩下的活需要超过 45 秒 → 立刻停下，报告：已经有什么、在哪；做完并确认了什么；还缺什么。
> - 如果剩下的活在 45 秒内做得完 → 用最短路径做完，报告结果。
> 窗口结束时节点会再被停一次，所以不要开始窗口内完不成的事。

我拿 20 秒预算去跑一条 300 秒的命令做验证，子 Agent 自己的回答是：

> My node's 20 s budget was already spent and only ~45 s remained, so I stopped waiting instead of starting anything else.

**它自己算出来"剩下的活 > 剩下的时间"，然后选择结束。** 跑完之后，系统里也没有残留进程。

## 实测：什么时候赢，什么时候输

我没有只挑好数据说。这个插件有些任务上真的快，有些任务上真的亏。

> 说明：下面的耗时是"归一化"后的。因为在大半天里，服务端的生成速度会波动五倍，直接比墙钟等于在比"服务端今天忙不忙"。归一化就是把生成速度固定成同一个值再比。

**赢的：**

| 任务 | 原生 | 本插件 |
|---|---:|---:|
| 5 道独立实现题 | 149s | **89s** |
| 5 道难题 | 81s | **78s** |
| 多元件代码审查 | 679s | **580s** |
| N 体优化 | 1272s | **646s**（token 少 5 倍）|

这类「读一点、想一点、再读一点」的任务，插件把零散的串行调用批成了整轮，明显更快。

**输的：**

| 任务 | 原生 | 本插件 |
|---|---:|---:|
| 短审查题 | 56s | 83s ✗ |
| 4 个 bug 定位 | 86s | 184s ✗ |
| 长程工程任务 | 828s | 1183s ✗ |

短任务输的原因很清楚：**「给每个节点估时间」这件事本身要花推理成本**，任务太短摊不回来。

长程工程任务输在**编队膨胀**：模型派了 10 个执行者，而简单版本只派 4 个。人多不一定快。

**还有一次有点讽刺的：**

同一个 2048 任务，用了节点预算之后：模型给 **9/9 个节点**都写了预算，那个原本跑 568 秒的执行者，这次在 **150 秒预算内、69 秒就完成了**。整局 513 秒，分数和之前几次完全一样。

**预算没有让分数变高，它只是让"超时"变成了"带着部分结果的超时"。**

## 适合谁，不适合谁

**适合：**

- 长任务、多步骤、能拆成互不相干部分的活；
- 需要「先规划再执行」的场景：改多个文件、跑多个实验、审查多个模块；
- 你希望子 Agent **继承当前对话**（看得到你这轮读过什么），而不是从零开始。

**不适合：**

- 特别短的任务——建图的固定成本比活本身还大；
- 强交互、必须看一步走一步的任务——这种交给 `tools` 节点一轮一轮推进更合适；
- 对**精确耗时**有严格要求的场景——模型估的时间只是"预期"，不是承诺。

dsh plugin install @zyn19940107/dsh-conductor

装完不需要改任何东西，插件会自动接管 Agent 的工作流。当前版本 **v2.4.0**。

如果你也在做 Agent 工作流，欢迎来聊——尤其想听两种反馈：

1. **你的真实任务里，模型会不会给节点写合理的时间预算？** 我的实测里它写得还行（2048 上 9/9 个节点都写了，而且有区分度：搜索 330 秒、修复 260 秒、执行者 150 秒），但样本还太少。
2. **短任务上这笔固定成本，有没有办法收回来？** 我目前的答案是「没有，接受它」——因为插件的价值在长任务上。但如果你有更好的想法，我很想听。
