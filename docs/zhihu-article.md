# 让 AI 干个活，它干着干着就跑偏了？我把它改成「公司」的方式

先别看标题，看看这几个场景你熟不熟悉：

- 你说「帮我改一下这个项目」，它改了 A 文件，B 文件炸了；你让它修 B，A 又炸了。
- 让它干一件事，它读了二十个文件，其中五个是刚才读过的——越到后面越糊涂。
- 最要命的一种：**它跑了十分钟，最后告诉你「没做完」**。你不知道它做到哪，它也没留下任何东西。

如果你遇到过，那问题大概率不是模型不够聪明。

**是我们让 AI 干活的方式，和真实世界里干活的方式，根本不是一回事。**

## 一、AI 现在是怎么干活的

现在几乎所有 AI Agent，底层都是同一个循环：

> 想一步 → 调一个工具 → 看结果 → 再想一步 → 再调一个工具 → …

「调工具」就是：读个文件、跑条命令、搜个网页。

做**小事**很好用。但活一大，就出四个问题：

1. **排队。** 三件互不相干的活，也得一件件做。
2. **记性差。** 每走一步都要把之前所有内容重看一遍，几十步后脑子全是中间结果，还经常忘记自己刚读过什么。
3. **没人管时间。** 它看不见钟表，一个活要干多久全凭它觉得「差不多了」。
4. **干到一半，什么都没留下。**

## 二、真实工作里，最贵的那个人不写代码

想想你公司接一个需求是怎么干的：

1. 不会立刻打开 IDE 写代码，先**想清楚这活怎么拆**；
2. 然后**决定每块交给谁**：自己干、给个纯执行的、还是给个能自己拿主意的；
3. 交代的时候说三句话：**做什么、多久要、回什么给我**；
4. 接到活的人，可以自己再往下分，也可以就自己干完。

一个系统从老板一句话到上线，中间要过项目经理、产品、开发、测试、运维——这些环节一步都省不掉。

**大模型提升的是每个环节的效率，不是让你跳过这些环节。**

我做的事就是：把这套「公司」的组织方式，塞进 AI Agent 的工作流里。

## 三、三层组织：领导、小领导、干活的人

我把它做成了一个插件，叫 **dsh-conductor**（中文名「公司工作流」）。

核心是一句话：

> **每一轮，AI 先当领导：不碰工具，纯粹想这活怎么拆、交给谁、多久要、回什么。想完写一张派工单，交给执行者。结果收回来，领导只看结果决定：能交差就收工，不能就再派一轮。**

执行者分三类，正好对应公司的三层：

| 层次 | 节点类型 | 是什么 |
|---|---|---|
| **领导** | 主模型自己 | 不动手，只负责拆活、派活、验收、汇报 |
| **小领导** | `forker` / `spawner` | 能**再派活**的负责人。自己拆图、自己派下属、自己汇总 |
| **干活的** | `worker` | 只能自己干，**派不了任何人** |
| （不是人）| `tools` | 一批机械调用，没有判断、没有结论 |

关键区别只有一条：**能不能把活再交给别人。**

- `worker` 拿不到画图的能力（调用会被拒绝），所以它一个下属都派不了，只能自己一口气干完；
- `forker` / `spawner` 能画图，所以它们能拆出并行节点、能派自己的 worker——它们是真的小领导；
- 区别只在于：`forker` 继承当前对话（知道你这轮读过什么），`spawner` 从空白开始（任务里要写全背景）。

而 `tools` 根本不是「人」——它是领导已经把参数定好的一批调用，插件照着执行，不产生任何判断。

顺带一个后来的修正（v2.10 起）：**worker 拿不到图里的 tools 节点，但拿得到一个同名的 `tools` 工具** ——
同一套调度、同样的结果截断，只是不需要画图。叶子节点也能把「一批只做收集的调用」打成一个批次，
而不用为它破例开一张图。

## 四、什么时候才需要「再一层领导」

这是我这段时间最有意思的发现。

直觉是「活越复杂越需要小领导」。**数据说不是。**

我拿一道长程题做对照：从零实现三个 Python 库（commit0，784 个隐藏测试）。

> 这一组是早期版本（v2.x，commit0 任务，各 2–3 次）的对照，不是 v2.10.2 的数据；样本小，
> 当方向性观察看。

| 组织方式 | 时间 | 正确性 |
|---|---:|---|
| 三个库各派一个 **worker**（干活的人）| 987 秒 | 784/784 |
| 三个库各派一个 **forker**（小领导）| **1718 秒（+74%）** | 784/784 |

**复杂度一样，正确性一样，多一层领导慢了 74%。**

为什么？因为三个库本来就在**父代理这一层**并行了——再给每个库配一个领导，等于「一个经理下面三个组，每个组只有一个固定流程的活，却给每个组又配了个组长」，多一层管理，没多出并行度。

那什么时候需要？我做了个验证任务：**三个模块的并行审查，必须由同一个负责人整体负责**。这种活一个人干不完（要并行），又必须一个人签字（不能拆给三个互不相干的人）——所以这个负责人需要能派活的下属。

结果：**3 次全部选了 forker**，每个 forker 在自己内部派了 3 个并行 worker 去审三个模块，60-99 秒完成。

**结论：不是「复杂 → 需要小领导」，而是「这一层有活要组织 → 需要小领导」。**

## 五、报告要像报告：结论，不是收据

这一条来自一个具体的失败。

早期版本里，父代理把「读文件、跑命令」都交给 tools，然后**自己把原始输出全读一遍**——名义上当领导，实际在当唯一的读者。一次 matpower 任务里，它 93%-97% 的上下文全是工具输出的原始文本。

我做了两件事：

**① 原始材料有上限，但节点不会消失。**

- 单个工具调用的输出：最多 10k 字符（头 6k + 尾 4k）；
- 一个 tools 节点的合并输出：最多 5k 字符，超了保留头尾，**标记里列出这个节点的每一个调用**；
- 但整份「计划报告」永远不截断——**每个节点一定出现在报告里**。

原始材料父代理不需要读，需要的时候下一轮再派一次调用就行。

**② 结论只讲实质。**

子代理回来的时候只交三段：查到了什么、大概怎么做的、结果如何。而且**不许带收据**：不要行号、不要文件路径、不要「证据」。

这里我犯过一个错，值得单独说：**我先做成了机制** —— 结论里只要出现「证据 / 行号 / proof / citation」这类词，整行在到达父代理之前删掉。

跑了一个月之后发现两件事：

- **提示词本来就够用**：130 份子代理报告里只有 17 份（13%）出现这类词，而且大半是任务本身在讨论这条规则时引用的；
- **删除会误伤**：一次 review 任务里，一个 worker 把「嵌套深度由 delegationDepth 把关」和「把含行号的句子剔掉」写在了同一段里，于是**整段消失**，父代理再也没看到 delegationDepth 这个事实，判据直接扣分。

现在这条删干净了（v2.10.2）：**提示词负责要求，输出就是模型写的**，插件不再静默篡改子代理的结论。

教训：**"先写后删"是个坏形状** —— 如果一条规则要求模型不要写某样东西，那就在提示里要求；用后处理去补救，等于既要模型遵守、又不信任它，最后两头都受伤。

## 六、还有那句「多久要」

这是最早的那个事故教我的。

我让 AI 玩一局 2048（15 分钟预算）。它发现游戏随机数固定，于是决定写个求解器离线搜索——思路完全正确。然后它把这个活交给一个子代理，**那个子代理跑了 568 秒，占掉整局 76%，最后什么都没交出来**。

AI 看不见钟表，所以「慢」不是最糟的——**最糟的是慢，而且什么都没留下**。

现在的做法分三层：

**① 每个节点可以写「预计多久」。** 到点了不直接杀。

**② 先让它跑完手上那条调用，再要报告。** 它可能就差一行；那条调用的时间已经付过了，杀掉就是白付。所以到点之后：不再开始新活，等在手调用返回，然后进入「报告模式」——拒绝一切工具调用，要求写现状报告（磁盘上有什么、确认了什么、还缺什么）。**报告本身不设时限**：API 慢不能把一个已经做完的活变成沉默。

**③ 写完报告，节点不结束。** 这是最新一版（v2.9 起）才想明白的：

- 子会话保持存活，上下文、文件、后台任务都留着；
- 下一轮计划里**出现同一个 node id**，就复用那个子会话，给它新预算接着干；
- 下一轮不给这个 id，就当场销毁（父代理认为没必要继续）；
- 循环结束，剩下的统一释放。

这样「预算到点」不再等于「这段工作作废」，而只是「暂停一下、报告进度、下一轮接着干」。

拿 20 秒预算去跑一条 180 秒的命令做验证，图在 210 秒返回，命令的输出完整躺在报告里。再拿 10 秒预算跑 30 秒的命令：第一轮报告并停泊，第二轮用同一个 id 接回——**实测整个过程中只创建了一个子会话**，是同一个 agent 接着干，不是重开一个。

## 七、实测：什么时候赢，什么时候输

⚠️ 先说清楚：这一节我返工过两次。第一次是测量错误（下面单独说），第二次是发现有一批运行被 API 限流打断、判据读到的是截断的回答。现在是 **v2.10.4、8 个任务、每臂 5 次、80 次运行**，4 路并发跑出来的，80 条记录全部无错误回合。

| 任务 | 类型 | 归一化时间 | token | 成本 | 正确性（案例级）|
|---|---|---:|---:|---:|---|
| **panel** | 三份互相独立的评审 | **0.54×** ✅ | **0.10×** ✅ | **0.19×** ✅ | 28/30 → 28/30 |
| 5 道难题 | 独立，较重 | **0.64×** ✅ | 1.40× | 1.56× | 25/25 → 25/25 |
| 三部分源码审查 | 读同一批文件 | **0.93×** | 1.03× | 1.23× | 28/30 → 27/30 |
| N 体优化 | 能拆，但要在同一份代码上迭代 | 1.10× | **0.46×** ✅ | **0.93×** ✅ | 20/20 → 19/20 |
| 5 道独立实现题 | 独立 + 轻 | 1.16× | **0.59×** | 1.17× | 25/25 → 25/25 |
| matpower | 单文件 + 严格规格 | 1.25× | **0.27×** ✅ | **0.87×** ✅ | 56/60 → **57/60** ✅ |
| 覆盖度问答 | 跨文件聚合 | **1.97×** ✗ | **0.31×** | **1.68×** ✗ | 25/25 → 24/25 |
| quixbugs | 4 个几十行的小 bug | **1.76×** ✗ | **2.98×** ✗ | **2.32×** ✗ | 20/20 → 20/20 |
| **几何平均** | | **1.07×** | **0.56×** | **1.04×** | 227/235 → 225/235 |

**只有 panel 是真的赚：时间 0.54×、token 0.10×、成本 0.19×，正确性还持平。**

panel 这道题要求「三份互相独立、互不知情的评审」。off 臂是一个代理顺序做三份，三份的源码阅读全累积在同一个上下文里（41.3M token）；插件臂把它变成并行 forker，各自独立上下文（4.1M token）。**独立性 → 并行 → 上下文隔离**，三个收益叠在一起。

**quixbugs 输得最惨：时间 1.76 倍、成本 2.32 倍。** 4 个几十行的小 bug，单代理 75 秒、6 分钱就做完了；插件臂派了 5 个人，每人一份上下文——**框架开销大于任务本身**。我后来专门为它改了两轮提示词（让父代理先读一轮再派、让节点不再自己跑全局验收），成本都没降下来：**瓶颈是"为每个几十行的小活开一个代理"，不是验证方式。**

**N 体那题的故事最曲折。** v2.10.2 时它是"时间快 16%、token 少 59%，但成本更高、正确性从 5/5 掉到 3/5"。查下来原因很具体：父代理把一个**写文件**的节点和一个**验证它**的节点放进了同一层，验证者只能轮询（实测 5 次 `Start-Sleep`、25–50 秒）等文件出现；那一轮文件被写了 14 次，它验证到的是中间版本，最终版本从没在判分器最严的 `global` 档跑过。顺带还有：判分器有 4 个档，父代理却把 criteria 写成"`check --scale 1k` 通过"——**判据比验收脚本窄**。这两条用提示词修完（v2.10.3 / v2.10.4），这一版 N 体变成：时间 1.10×、token 0.46×、成本 0.93×，正确性 20/20 → 19/20。

所以这个插件**不是"全面更快"** —— 它只在「子任务真的互相独立、且单个子任务足够重」时划算。

## 八、我在这套数字上犯过的四个错误

这段可能比结果本身更有用。

**错误一：token 算重了。** fork 出来的子会话，日志开头是父对话的拷贝，里面带着父代理自己的 token 用量。我按整个日志累加，等于把父代理的 token 按子代理数量重复计了一遍——单条记录虚高 0%–24%，on 臂的系统性偏高。修法：在 `end-seed` 边界切开，只算子会话自己的。

**错误二：并发跑坏了工作区。** 同一条件的 5 次重复共用一个工作区，而每次 setup 都会重建它。我并发跑 5 次，它们互相把对方的 `solution.py` 重置成空模板。症状极其迷惑：**worker 报告「RESULT 5/5」，判据却判 0/5**——因为判据运行时文件已经被另一次运行清空了。我一开始还以为是模型在撒谎。修法：工作区路径带上运行序号。

**错误三：样本太少就下结论。** 同一个任务单次运行的 token 能从 86 万波动到 324 万。我拿 5 次的中位数讲「省了 24%」，其实那是噪声。

**错误四：把被限流打断的运行当成了结果。** 最后一轮 80 次跑完，我先看到 panel 的 off 臂只有 1/5 正确、token 还低了 60%——差点写成「插件在 panel 上也不行了」。查会话日志才发现：4 次 off 运行在跑到一半时被 API 限流（429）打断，判据读到的是一段被截断的回答。**跑分脚本只看退出码，退出码是 0**——它把「这个进程没崩」当成了「这次运行有效」。修法：每条记录的 `turn/end` 都检查 `kind: error`，有错误回合的一律重跑。重跑后 panel 两臂都是 28/30。

四条修完之后，之前那些「省一半」「快 12 倍」的漂亮数字全没了。这大概就是测量的意义：**它先拆掉你自己的故事**。

## 九、什么活适合，什么活不适合

**适合：**

- 子任务之间**真的独立**、而且每个子任务都**足够重**的活（panel 是典型：三份互不知情的评审）；
- 需要先规划再动手的：改多个文件、跑多组实验、分头审查几个模块；
- 你希望接活的人**看过你之前读过的东西**，而不是从零开始。

**不适合：**

- 几十秒就能做完的小事——建图、估时间、继承上下文的固定成本摊不回来（quixbugs 就是教训）；
- 必须看一步走一步的强交互任务；
- 单文件、严格规格、反复调试的工程活（matpower）——能拆的是"验证"，不是"实现"；
- 以及：**不要指望它提高正确率**。这一版里它甚至在两道长程题上让正确性变差了。

## 最后

项目在 **github.com/zyn19940107/dsh-conductor**，当前 **v2.10.4**，装完不用改任何东西。

写这个插件最大的收获不是代码，是想明白一件事：

> **AI Agent 现在缺的往往不是能力，是「怎么组织工作」。**

我们花了十几年把「需求→架构→方案→开发→测试」这套流程打磨出来，不是为了在 AI 时代把它扔掉——而是把它交给 AI。

如果你也在做 Agent 工作流，欢迎来聊。尤其想听两种反馈：

1. **你的任务里，模型会不会正确判断「这活该不该再派一层」？** 我这边它只在结构确实需要时才选 forker，但样本还少。
2. **短任务上这笔固定成本，怎么才能收回来？** 我目前的答案是「收不回来，接受它」。
