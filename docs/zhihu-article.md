# dsh-conductor：把公司的工作方式搬进 Agent

## 先说一个我踩过的坑

我在用一个 agent 跑了 15 分钟的 2048 任务。

模型很聪明，它发现这个游戏的随机数种子是固定的、引擎是确定性的，于是决定「不复盘、直接离线搜索」——写一个求解器，跑出最优走法。想法完全合理。

于是它派了一个子代理去做这件事。

问题出在：**这个子代理跑了 568 秒，占掉整次运行的 76%，最后什么都没交出来。**

父代理在超时之后才发现被吃掉了预算，它的原话是：

> The worker timed out (540s budget = 9 min!). That ate a lot of my 15-minute budget.

更糟的是：那个子代理其实**没有空转**——它写了 22 步、30 次工具调用，真的在写代码、调 bug、跑求解器。它只是**把时间花在了一个太贵的方向上，而且没有人叫停它**。

这次失败让我意识到一个问题：**问题不在模型不够聪明，在于 agent 的工作流本身不对。**

## 原生循环：想一步，做一步，再看一步

DeepSeek Harness（以及绝大多数 agent 框架）原生的循环是：

```
想一步 → 调一个工具 → 看结果 → 再想一步 → 再调一个工具 → …
```

这个循环适合短任务。但把它放到长任务上，会暴露几个很实际的问题：

**1. 串行。** 模型一次调一个（或少数几个）工具，明明三件互不相干的活，也要排队做。

**2. 上下文滚雪球。** 每一步都要把完整的对话重新发一遍，几十步之后，上下文里全是中间结果。而且模型会反复读同一个文件——它记不住自己三步前读过什么。

**3. 没人管时间。** 模型看不见时钟。它只能「估计」当前进度，而且估得经常不准。一个节点跑多久，全凭它自己觉得「差不多了」。

**4. 结果会被静默截断。** harness 对超大的工具结果有 spill 策略，到了一个上限就只保留头尾。但模型不知道中间被切了，它以为那是全部。

**5. 最重要的一点：这不是真实工作的组织方式。**

## 真实工作里，没有人「想一步做一步」

想一想你在公司接一个需求会怎么做：

1. 你不会立刻打开 IDE 开始写代码。你会先**想清楚这活怎么拆**；
2. 然后**决定每一块交给谁**：自己干？给一个纯执行的同学？还是给一个也会自己拆活的同事？
3. 交代的时候一定会说三件事：**要做什么、多久要、回什么结果给我**；
4. 接到活的人**可能继续当领导**（自己再拆一层），也可能只是纯干活。

**领导的价值在于：他不动手，但他决定怎么分、分给谁、什么时候要、以及拿回来的东西够不够做决定。**

我把这套结构直接搬进了 DeepSeek Harness，做成一个插件：**dsh-conductor**（中文名就叫「公司工作流」）。

## 设计：四个角色 + 三件事

插件把「执行者」分成四种：

| 角色 | 插件里的名字 | 是什么 |
|---|---|---|
| **领导** | 每一轮的主模型 | 不动手，纯思考：怎么拆、交给谁、多久、回什么 |
| 纯执行者 | `tools` | 参数已经定好的一批工具调用，不再思考、不再拆分 |
| 干活型执行者 | `worker` | 继承当前对话，自己开工，不画图 |
| 能再当领导的执行者 | `spawner` / `forker` | 自己再拆一层，继续走这套工作流 |

每一轮固定四步：

```
① 想图：这一轮有哪些活、每个节点是什么角色、交付什么、大概花多久
② 交图：主模型不调任何工具，第一条消息就是图
③ 执行：所有节点同时开始（只有一层），结果一起回来
④ 判断：只看结果——能回答就写结论结束，不能就画下一张图
```

**关键点：这四件事没有一件是插件规定死的。** 怎么拆、交给谁、要多久、回什么，全部由模型自己决定。插件只负责提供机制。

## 为什么这些必须是「机制」，不能只是「提示」

这是我在开发过程中感受最深的一点。

提示词写在系统提示词里，模型会把它当成背景音。我试过把同样的要求放在系统提示词的不同位置——**改位置没用**。真正有用的是把它做成**最后一条消息**、或者做成**扩展点上的硬拦截**。

所以我做了五个机制：

**1. 每轮的第 1 步之前，插件把「四步循环」作为最后一条消息塞进去。** 系统提示词在最前面，模型说话前最后读到的才是它真正会照做的东西。

**2. 图跑完之后，模型自己发起的工具调用一律拒绝。** 那是「判断」阶段：要么写结论，要么交下一张图。不许在这里继续一个一个调工具干活——那是图里的活。

**3. 派发只能走图。** harness 自带的 `subagent` / `subagent_fork` 直调会被拒绝，并提示改成图里的节点。否则模型会绕过这一轮的结构，直接开子代理——那等于没有结构。

**4. 计划报告永远不截断。** 计划跑完后，所有节点的结果会一起返回给模型，这是它做判断的唯一依据。如果这份报告被 harness 的流量控制截断，中间某个节点就等于**静默消失**了。插件在 `tools/post-execute` 上用一个带 `value` 的决定返回结果，harness 的 spill 策略会跳过它。

**5. 后台子代理的管理工具从工具表里移除。** 计划节点是同步的，没有「后台子代理」这个可管理的东西。模型拿到 `list_agents` / `send_message` 这些工具只会空转——我实测有样本在 `Start-Sleep 120` 里循环了 47 步。

## v2.3 的核心：每个节点都要说「我大概花多久」

这就是开头那个 568 秒事故的直接产物。

**问题是：模型看不见时钟，它只能推测。** 所以「慢」本身不是最糟的——最糟的是「慢，而且最后什么都没留下」。

直接杀掉是最差的处理：节点做了一半的东西全部作废，父代理也不知道它做到哪。

我的做法是：**图里每个节点都声明一个 `budgetMs`（预计花多久）。预算用尽时，插件先停下、再让节点自己交代。**

- 对 `tools` 节点：中止还没跑完的调用，**保留已经跑完的**，在报告末尾标一行「预算用尽，未完成的已停止」；
- 对 `worker` / `forker` / `spawner`：先 cancel 掉当前回合（正在等的那条工具调用会被 abort，前台子进程随之被杀），然后注入一条消息——**花了多少、还剩多少、两种选择的后果**——让它自己决定「最短路径收尾」还是「报告现状结束」。

那条消息不是一句「看看状态」，而是给出它做判断需要的数字：

> 你的节点预算 20 秒已用完，正在进行的工作刚被停下。你现在最多还有 45 秒。
> - 如果剩下的活需要超过 45 秒 → 立刻停下，报告：已经存在什么、在哪；哪些做完并确认了；还缺什么。
> - 如果剩下的活在 45 秒内做得完 → 用最短路径做完，报告结果。
> 窗口结束时节点会再被停一次，所以不要开始窗口内完不成的事。

我拿 20 秒预算去跑一条 300 秒的 `python sleep` 做验证，子代理自己给出的回答是：

> My node's 20 s budget was already spent and only ~45 s remained, so I stopped waiting instead of starting anything else.

它自己算出来「剩下要做的 > 剩下的时间」，然后选择结束。跑完之后，系统里没有残留的 python 进程。

## 实测：什么时候赢，什么时候输

我没有只挑好数据说。这个插件在有些任务上是真的快，在有些任务上是真的亏。

**赢的（归一化耗时，越小越好）：**

| 任务 | 原生 | 本插件 |
|---|---:|---:|
| humeval | 149s | **89s** |
| humeval-hard | 81s | **78s** |

这两类「读一点、想一点、再读一点」的任务，插件把零散的串行调用批成了整轮，明显更快。

**输的：**

| 任务 | 原生 | 本插件 |
|---|---:|---:|
| coverage（短任务）| 56s | 83s ✗ |

coverage 是一道很短的只读审查题。插件输的原因很清楚：**「每个节点写预算」这件事本身要花推理成本**，短任务摊不回来。任务一长，这笔成本就被摊薄了。

**还有一次运气好到有点讽刺的：**

同一个 2048，用了节点预算之后：模型给 **9/9 个节点**都写了预算，那个原本跑 568 秒的 worker，这次在 **150 秒预算内、69 秒就完成了**。整次运行 513 秒，分数和之前几次完全一样（4.7852）——**预算没有让分数变高，它只是让「超时」变成了「带着部分结果的超时」**。

## 适合谁，不适合谁

**适合：**

- 长任务、多步骤、可以拆成互不相干部分的活；
- 需要「先规划再执行」的场景（改多个文件、跑多个实验、审查多个模块）；
- 你希望子代理**继承当前对话**（它看得到你这轮已经读过什么），而不是从零开始。

**不适合：**

- 特别短的任务——建图的固定成本比活本身还大；
- 强交互、必须看一步走一步的任务——这种活交给 `tools` 节点一轮一轮推进更合适；
- 对**精确耗时**有严格要求的场景——模型估的时间只是「预期」，不是承诺。

## 装一下试试

仓库在 GitHub：**github.com/zyn19940107/dsh-conductor**（改名前叫 dsh-refine-loop）

```
dsh plugin install @zyn19940107/dsh-conductor
```

装完之后不需要改任何东西，插件会自动接管 agent 的工作流。当前版本是 **v2.3.0**。

如果你也在做 agent 工作流相关的东西，欢迎来聊——尤其想听两种反馈：

1. **你的真实任务里，模型会不会给节点写合理的时间预算？** 我的实测里它写得还行（2048 上 9/9 个节点都写了，而且数值有区分度：搜索 330s、修复 260s、worker 150s），但样本还太少。
2. **短任务上这笔固定成本，有没有办法收回来？** 我目前的答案是「没有，接受它」——因为插件的价值在长任务上。但如果你有更好的想法，我很想听。
